## 1. Lab Phase Context + Capacity

### Why a Research Lab?

nox-mem is built on the conviction that **Quality** is the primary competitive moat — not features, not marketing. The Q/A/P strategic pivot (2026-05-17) formalizes this: the system's hybrid retrieval architecture must remain empirically defensible against any challenger, at any time, with honest published numbers.

The Lab exists to pursue paper-grade improvements that the product roadmap cannot absorb — experiments that may fail, take longer than a sprint, or produce negative results that are nonetheless published.

### Capacity Model

Post-launch capacity splits as follows:

| Bucket | Allocation | Examples |
|---|---|---|
| **Lab** | **40%** | Experiments, ablations, paper updates, benchmark runs |
| Product maintenance | ~25% | Bug fixes, schema migrations, community issues |
| GTM / nox-supermem | ~20% | Pricing, onboarding, Stripe integrations |
| Community response | ~15% | GitHub issues, PR reviews, Discord |

The 40% Lab allocation is **protected**. Product feature requests do not pre-empt Lab weeks unless a critical regression requires it.

### Quarterly Cadence

Each calendar quarter allocates **4 dedicated Lab weeks** distributed across the quarter (not necessarily contiguous). Q1 2026 spans **July–September 2026**, immediately following the expected GTM launch window (June 2026).

| Lab week | Target window | Primary focus |
|---|---|---|
| Lab W1 | Early Jul 2026 | EverMemBench setup + corpus acquisition |
| Lab W2 | Mid Jul 2026 | EverMemBench run + neural reranker baseline |
| Lab W3 | Mid Aug 2026 | Scale stress test + multilingual dataset curation |
| Lab W4 | Early Sep 2026 | Salience optimization + Q1 review write-up |

### Output Expectations

Each Lab quarter produces:
- **1–2 publishable findings** (audit doc or paper PR): positive, negative, or null results all count
- **Pre-registered specs** before work starts (see [§4 Governance](#4-lab-governance))
- **Quarterly review doc** at end of quarter summarizing findings and Q2 priorities

This plan is cross-linked to the Q/A/P strategic decision documented in `docs/DECISIONS.md` (D47 caminho C) and the research parking lot in `docs/ROADMAP.md §6`.

## 2. Q1 2026 Research Priorities

Priorities are ranked by a composite of three factors:
- **(a) Product-blocking:** does this finding block a future product milestone or paper update?
- **(b) Competitive-gap:** does this address a known weakness vs published competitors (EverMind, Mercury, MemGPT)?
- **(c) Scientific contribution:** does this produce a finding novel enough to merit a paper update?

---

### Priority 1: EverMemBench Evaluation (highest)

**Ranking rationale:** Highest priority because it simultaneously closes the primary competitive benchmark gap (b) AND blocks the paper §6.5 future-work claim (a) AND produces a publishable result regardless of outcome (c).

#### Motivation

EverMind (EverMind-AI, 5k+ stars) publishes results on EverMemBench — their own benchmark that has become a de-facto standard in the long-term agent memory literature. nox-mem currently uses the internal LongMemEval golden set (n=100, entity-flavored) and the Wave A entity-eval-v2 corpus (~500 queries). These are rigorous internally but are not directly comparable to EverMind's published numbers.

The benchmark gap creates legitimate "abandonware suspicion" for evaluators who expect standardized eval: if nox-mem cannot be compared on EverMemBench, the Q claim is unfalsifiable from the outside.

This experiment closes that gap. The result may be favorable (nox-mem matches or exceeds EverMind), neutral (comparable with different strengths), or unfavorable (EverMind outperforms on their home benchmark). All three outcomes are publishable; the unfavorable case provides the most valuable scientific data.

#### Scope

- Acquire EverMemBench full dataset and evaluation harness from the EverMind-AI repository
- Establish evaluation isolation: dedicated eval DB, `_check_eval_isolation()` guard, `NOX_DB_PATH` explicit override (per `[[eval-harness-must-explicit-isolate-db]]` lesson)
- Run nox-mem at current configuration (G10d Hard Mutex + section_boost + source_type_boost) against EverMemBench
- Record nDCG@10, MRR, Recall@k metrics using EverMemBench's own scoring scripts — not nox-mem's internal scorer
- Compare against EverMind published numbers in their paper (EMNLP 2025 or equivalent)
- Write honest comparison: where nox-mem leads, where it lags, and why

#### Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| nox-mem underperforms on EverMemBench | Medium | Publish the gap honestly; analyze root cause; plan targeted fix for Q2 |
| EverMemBench corpus inaccessible / license-restricted | Low | Contact EverMind team; fall back to LoCoMo or LOCRET benchmarks |
| EverMemBench favors conversation-heavy memory (vs entity-flavored) | Medium | Note evaluation domain mismatch in publication; this is scientifically valid |
| Eval contamination via main DB | Low | `_check_eval_isolation()` mandatory; lesson cravada from incident 2026-05-19 |

#### Outputs

| Artifact | Path | ETA |
|---|---|---|
| Pre-registration spec | `specs/lab-q1-evermembench.md` | Before Lab W1 |
| Results audit | `audits/2026-08-XX-evermembench-results.md` | End Lab W2 |
| Paper update | `paper/paper-tecnico-nox-mem.md` §6.5 | End Lab W2 + 1 week |

**Time estimate:** 2 weeks (1 week setup + corpus acquisition; 1 week run + analysis + write-up)

**Dependencies:**
- EverMemBench corpus accessible (public or via direct contact with EverMind team)
- nox-mem evaluation harness stable post-D49/D50 decisions

### Priority 2: Neural Reranker Exploration (high)

**Ranking rationale:** Cross-encoder reranking is a well-established technique with documented +3–8% nDCG@10 improvements in the IR literature. It extends the current 3-layer retrieval stack (FTS5 → Gemini semantic → RRF) with a 4th layer. Blocks a future paper §6.3 addition and addresses the competitive gap vs systems that use neural reranking.

#### Motivation

The current retrieval pipeline terminates at RRF fusion (k=60). The literature consistently shows cross-encoder rerankers improve precision in the final ranking pass, particularly for queries where semantic similarity and lexical overlap diverge. G-series ablations (G1–G11) have optimized within the current 3-layer architecture; neural reranking represents the most promising next architectural step.

The key constraint is the **Autonomy pillar**: nox-mem's data stays local or on user-controlled infrastructure. This rules out Cohere Rerank (cloud API, data leaves user control). BGE-reranker-v2-m3 (HuggingFace, Apache 2.0) is the primary candidate — runnable locally via Ollama or directly via ONNX.

#### Scope

Experiment series: **A11–G15 ablations** with reranker as Layer 4 (post-RRF, pre-response):

| Experiment | Configuration | Hypothesis |
|---|---|---|
| A11-baseline | Current G10d config, no reranker | Baseline nDCG@10 (expect ~0.62 on entity-eval-v2) |
| A12-bge-v2 | + BGE-reranker-v2-m3 (top-20 candidates → rerank → top-10) | +3–8% nDCG@10 |
| A13-bge-v2-top40 | + BGE-reranker-v2-m3 (top-40 candidates) | Diminishing returns check |
| A14-cross-enc-ms | + ms-marco-MiniLM-L6 (lighter, faster) | Speed/quality tradeoff |
| A15-latency | A12 config with p50/p95/p99 latency measured | Latency regression check (Q3 baseline: p50=940ms) |

Layer 4 integration point: after RRF produces ranked list, pass top-N candidates to cross-encoder, get scores, re-sort. The reranker receives `(query, chunk_text)` pairs — no schema changes required.

**Autonomy constraint:** All model candidates must run locally or on user-controlled infra. GPU resource (Modal/Replicate) is acceptable for Lab experiments but the production integration must have a CPU-viable fallback.

#### Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Reranker adds >500ms latency (violates product SLA) | Medium | CPU inference profiling in A15; gate production deployment on p95 < 1500ms total |
| BGE-reranker underperforms published figures on nox-mem eval | Medium | nox-mem eval is entity-flavored (different from MS-MARCO fine-tuning domain); document domain gap |
| Reranker nullifies section_boost/Hard Mutex gains | Low | Ablate with/without mutex in G15; if redundant, Hard Mutex may be removed |
| GPU resource budget for Lab experiments | Low | Modal Serverless ~$0.001/min A10G; 3-week experiment budget < $20 |

#### Outputs

| Artifact | Path | ETA |
|---|---|---|
| Pre-registration spec | `specs/lab-q1-neural-reranker.md` | Before Lab W2 |
| Ablation results | `audits/2026-08-XX-neural-reranker-ablations.md` | End Lab W2 |
| Paper update (if +5%+) | `paper/paper-tecnico-nox-mem.md` §4.4 | End Lab W3 |

**Time estimate:** 3 weeks (1 week setup + integration; 1 week ablation runs; 1 week analysis + write-up)

**Dependencies:**
- BGE-reranker-v2-m3 locally runnable (Ollama or direct ONNX inference)
- eval-v2 harness stable and isolated
- A15-baseline latency measurement reproduced (Q3 baseline: p50=940ms, p95=2342ms — these numbers should be re-measured post-G10d before comparison)

### Priority 3: Scale to 250k+ Chunks (high)

**Ranking rationale:** nox-mem's current production corpus is ~68k chunks (g5.db) and ~69k (g9.db). The product's viability for power users depends on maintaining retrieval quality and latency at 3–5× current scale. This experiment reveals bottlenecks before they become production incidents.

#### Motivation

The current architecture uses SQLite (FTS5 + sqlite-vec) on a single VPS (Hostinger KVM4, 8GB RAM, 4 vCPU). SQLite is known to scale well for read-heavy workloads up to ~1M rows, but the FTS5 index and sqlite-vec vector store have different scaling characteristics. The Gemini embedding API (batch-limited, rate-limited at 1500 RPM for gemini-embedding-001) is the suspected primary bottleneck for ingestion.

A target of **250k chunks** (~3.6× current prod) represents a realistic 18-month growth trajectory for a power user ingesting daily across multiple workspaces.

#### Scope

- Generate or acquire a **synthetic corpus** of 250k chunks with realistic characteristics:
  - Mix of entity files, markdown docs, conversation logs, code snippets
  - PT-BR and EN content (ratio ~30/70 matching expected user distribution)
  - Realistic chunk sizes (200–600 tokens per chunk, consistent with current distribution)
- Ingest corpus into isolated eval DB (never touch main DB — lesson from incident 2026-05-19)
- Measure at 50k / 100k / 150k / 200k / 250k checkpoints:
  - Ingestion throughput (chunks/min, embed API calls/min, failures)
  - Search latency (p50/p95/p99 for hybrid BM25+semantic+RRF query)
  - Memory footprint (RAM during search, VPS limits)
  - FTS5 index size and query plan (EXPLAIN QUERY PLAN)
  - sqlite-vec query time vs vector count

**Hypothesis:** FTS5 should remain fast at 250k (SQLite FTS5 scales to millions of rows). sqlite-vec query time scales linearly with vector count; expected p50 degradation < 200ms at 250k. The Gemini embedding API rate limit (~1500 RPM) means full ingestion of 250k chunks takes ~3–4 hours at max rate — acceptable for a background process.

#### Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Synthetic corpus lacks realistic diversity | Medium | Use subset of publicly available datasets (Wikipedia, Stack Overflow, CC-News PT-BR) augmented with template generation |
| sqlite-vec scales worse than expected | Medium | If degradation > 300ms at 250k, evaluate chunked HNSW index or batch-vector approach |
| Gemini API quota exhaustion during test | Low | Use dedicated Gemini project key with elevated quota for Lab week; do not use production key |
| VPS OOM at 250k | Low | Monitor `/proc/meminfo` during test; abort at 80% RAM usage; note failure point |

#### Outputs

| Artifact | Path | ETA |
|---|---|---|
| Pre-registration spec | `specs/lab-q1-scale-stress.md` | Before Lab W3 |
| Stress test results | `audits/2026-08-XX-scale-stress-250k.md` | End Lab W3 |
| Architecture note (if bottleneck found) | `docs/adr/ADR-XXX-scale-ceiling.md` | End Lab W3 |

**Time estimate:** 2 weeks (1 week corpus setup + tooling; 1 week measurement runs + write-up)

**Dependencies:**
- Synthetic corpus generator OR partner with a user who has a large corpus (250k+ chunks) willing to share anonymized data
- Isolated eval VPS or Lab VM with equivalent specs to production (Hostinger KVM4)
- Gemini API project with Lab-specific key (not production key — see `[[no-secrets-in-git]]` lesson)

### Priority 4: Multi-lingual Evaluation (medium)

**Ranking rationale:** nox-mem's primary user base is PT-BR (Toto's audience), but the paper and competitive positioning claim multi-lingual capability via Gemini embedding (which is multi-lingual by design). This claim needs empirical validation. Ranked medium because it does not block the paper or product milestone, but does strengthen the Autonomy pillar's value for international markets.

#### Motivation

Gemini embedding (`gemini-embedding-001`) is trained on multi-lingual corpora and performs competitively on cross-lingual tasks in Google's internal benchmarks. However, nox-mem has not independently validated this claim on its specific query patterns (temporal, entity-centric, adversarial). The internal golden set is EN-only. PT-BR users (the primary target market) have no eval coverage.

Multi-lingual eval also tests whether the FTS5 BM25 layer degrades for non-Latin scripts or heavily diacriticized text (PT-BR accented characters showed `\b` boundary failures in `[[js-regex-unicode-word-boundary-fails]]` — FTS5 may have analogous issues).

#### Scope

Language targets for Q1 (in priority order):
1. **PT-BR** — primary market; ~50 golden queries covering daily conversation, technical terms, finance vocabulary
2. **ES** — Latin American secondary market; ~25 queries
3. **DE** — European market reference; ~25 queries (German compound words stress tokenizer)
4. **FR** — European market secondary; ~25 queries

For each language:
- Curate 25–50 golden queries with known correct answers in the chunk corpus
- Run hybrid search and record nDCG@10, MRR@10
- Compare against EN baseline (same query semantics, translated)
- Profile whether degradation is in FTS5 layer, semantic layer, or RRF fusion

**Native speaker requirement:** Dataset curation for each language must involve a native speaker review pass. Community contributions welcome (see [§5](#5-open-questions--external-collaborators-welcome)).

#### Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Gemini embedding underperforms on PT-BR vs EN | Medium | Expected; document delta; if > 10% nDCG gap, flag for language-specific embedding evaluation |
| FTS5 tokenizer degrades on accented characters | Medium | FTS5 uses Unicode-aware tokenizer by default; validate with `\p{L}` whitelist sanitize (lesson `[[unicode-aware-sanitize-for-fts5]]`) |
| Native speaker availability for dataset review | High | Community-first: open GitHub issue inviting native speakers; do not publish without review |
| Dataset construction takes > 1 week | Medium | Scope PT-BR only for Q1 if time-constrained; ES/DE/FR move to Q2 |

#### Outputs

| Artifact | Path | ETA |
|---|---|---|
| Pre-registration spec | `specs/lab-q1-multilingual.md` | Before Lab W3 |
| Eval datasets | `eval/multilingual/<lang>-golden-v1.jsonl` | Lab W3 |
| Results audit | `audits/2026-09-XX-multilingual-eval.md` | End Lab W4 |

**Time estimate:** 3 weeks (1 week dataset curation; 1 week eval runs; 1 week analysis + review)

**Dependencies:**
- Native speaker collaborators for PT-BR, ES, DE, FR review
- Existing chunk corpus with multi-lingual content (at least PT-BR — currently ~30% of nox-mem production corpus is PT-BR)
- FTS5 sanitize fix confirmed in production post-PR-`[[unicode-aware-sanitize-for-fts5]]`

### Priority 5: Salience Formula Optimization (medium)

**Ranking rationale:** The G10d Hard Mutex deployment represents the practical ceiling of hand-tuned boost coefficients. The next-generation approach is automated weight search. Ranked medium because the current formula is deployed and working (+0.79% nDCG / +2.65% MRR vs no-mutex); optimization risk is real and must be managed carefully.

#### Motivation

The salience formula v2 (deployed 2026-05-21) uses hand-tuned weights:
```
salience = W_IMPORTANCE×importance + W_RECENCY×recency_score + W_PAIN×pain + W_ACCESS×access_score
W_IMPORTANCE=0.55, W_RECENCY=0.15, W_PAIN=0.10, W_ACCESS=0.20
```

The G-series ablations (G7–G11) established that the formula is **neutral in shadow mode on small corpora** and only contributes meaningfully at production scale (G7: Δ+0.5% noise in eval; meaningful in g5.db 68k corpus). The current weights are based on intuition and a limited grid search (PR #169). Bayesian Optimization (BO) or CMA-ES could find weights that generalize better across query types (single-hop, multi-hop, temporal, adversarial).

**Key constraint:** Hyperparameter search must be cross-validated against a **held-out eval set** that was not used in any prior ablation. Otherwise overfitting to G-series query distribution is guaranteed. This requires constructing a fresh held-out set before optimization begins.

#### Scope

Phase 1 (Lab W3–W4): held-out set construction
- 50 queries drawn from nox-mem production logs (anonymized, deduplicated, novel)
- Does NOT include any query from LongMemEval n=100 or entity-eval-v2 (those are training/validation)
- Native speaker review if PT-BR queries included

Phase 2 (Lab W4): automated search
- **BO approach:** Optuna with TPE sampler; 200 trials; objective = held-out nDCG@10
- **CMA-ES approach:** `cma` Python package; 150 generations; same objective
- Search space: W_IMPORTANCE ∈ [0.40, 0.70], W_RECENCY ∈ [0.10, 0.25], W_PAIN ∈ [0.05, 0.20], W_ACCESS ∈ [0.10, 0.30] (constrained to sum = 1.0)
- Cross-validate winning weights on entity-eval-v2 before any deployment consideration

**Decision gate:** If optimized weights improve held-out nDCG@10 by < 1.0%, the current hand-tuned weights are retained. If ≥ 1.0%, weights advance to shadow mode for 7-day baseline before deployment (established pattern per `[[ship-ranking-changes-in-shadow-mode-first]]`).

#### Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Overfitting to held-out set | Medium | Cross-validate on entity-eval-v2 before any deployment |
| BO search takes >4 weeks at scale | Low | Cap at 200 trials (~4h on CPU for fast eval; use g9.db-sized corpus) |
| Optimal weights destabilize Hard Mutex behavior | Low | Run G12-style per-category audit on optimized config before advancing |
| Net result: current weights are optimal | Medium | Valid outcome; publish as "weights are robust to optimization" — still a scientific finding |

#### Outputs

| Artifact | Path | ETA |
|---|---|---|
| Pre-registration spec | `specs/lab-q1-salience-opt.md` | Before Lab W3 |
| Held-out eval set | `eval/held-out-v1.jsonl` (50 queries) | Lab W3 |
| BO/CMA-ES results | `audits/2026-09-XX-salience-optimization.md` | End Lab W4 |

**Time estimate:** 4 weeks (2 weeks held-out construction; 2 weeks search + validation + write-up)

**Dependencies:**
- Production query logs accessible (anonymized via session scrubbing)
- PR #55 (I1 env vars for salience weights) merged — enables runtime weight injection without recompile
- `python3` + `optuna` + `cma` available in Lab environment

## 3. Quarterly Review Process

### End-of-Q1 Review (target: late Sep 2026)

The Q1 review produces a single document: `docs/research/Q1-2026-review.md`. It covers:

1. **Findings summary** — one paragraph per priority, honest about results (positive, negative, null)
2. **Metric impact** — for each experiment: nDCG@10 delta vs G10d baseline, with error bars
3. **Q2 priority decisions** — three outcomes per item:
   - **Advance:** move to Q2 research agenda (deeper investigation)
   - **Graduate to product:** hand off to nox-supermem or main nox-mem roadmap as a feature
   - **Park / kill:** insufficient signal or risk; document why

### Decision Authority

| Decision type | Authority |
|---|---|
| Kill a Lab experiment (negative result) | Lab lead (no escalation required) |
| Graduate to product (requires product effort) | Lab lead + Toto sign-off |
| Change Q1 priority mid-quarter | Lab lead; document in spec amendment |
| Allocate > 40% to Lab in a given week | Toto approval required |

### Q2 Planning

Q2 planning begins in late September 2026 following the Q1 review. Q2 priorities are seeded from:
- Unfinished Q1 work (explicitly scoped-down items)
- Follow-up experiments from positive Q1 findings
- New parking-lot items accumulated during launch/GTM
- Community requests that have scientific validity

## 4. Lab Governance

### Pre-Registration

**Every Lab item requires a spec before work starts.** The spec lives at `specs/lab-q1-<name>.md` and defines:
- Hypothesis (falsifiable)
- Exact metrics (what counts as success)
- Eval corpus identity (dataset hash + chunk count)
- Decision gate (what threshold triggers advancement vs parking)
- Time budget (hard cap)

Pre-registration prevents post-hoc rationalization of results. A finding without a pre-registered spec is not publishable as a Lab finding.

### Reproducibility

Every Lab experiment output must include:
- **Runner code** committed to `scripts/lab/` or `eval/` (no ephemeral notebook-only experiments)
- **Dataset hash** (SHA256 of the eval corpus DB or JSONL file)
- **Exact nox-mem version** (`git rev-parse HEAD` at time of run)
- **Environment** (Node version, sqlite-vec version, Gemini model version)

Without these four artifacts, the experiment cannot be replicated and is not considered complete.

### Publication

Every Lab item produces a published artifact regardless of outcome:
- **Positive result:** `audits/<date>-<name>.md` + potential paper PR
- **Negative result:** `audits/<date>-<name>-null.md` — describes what was tried, why it did not work, and what future approaches might succeed
- **Inconclusive:** `audits/<date>-<name>-inconclusive.md` — describes confounders and what would be needed to resolve

Null and inconclusive results are **explicitly valued**. The D47 decision (caminho C: "narrativa pain-weighted hybrid DEFENSÁVEL via G3" — honest framing over cherry-picking) applies to Lab equally: cherry-picked positive-only reporting would undermine the Q pillar.

### Honest Framing

If EverMemBench shows nox-mem trailing EverMind on their benchmark: publish the gap, analyze why, and describe the targeted fix. Do not suppress the result or narrow the evaluation scope post-hoc to make nox-mem look better.

This is cross-linked to `docs/DECISIONS.md` D47 (caminho C reframe): the entire competitive narrative rests on being the system that publishes honest numbers. One suppressed negative result destroys that credibility faster than the result itself would.

### Shadow-Mode Discipline

Any Lab finding that proposes a ranking or scoring change must enter **shadow mode** for ≥7 days on production traffic before deployment. This is a hard rule, not a suggestion — established via incident analysis and cravada in `[[ship-ranking-changes-in-shadow-mode-first]]`.

## 5. Open Questions / External Collaborators Welcome

nox-mem is an open-source project (MIT license). Lab research benefits from external expertise and community involvement. The following areas explicitly invite collaboration:

### BO/CMA-ES Hyperparameter Search

We have limited expertise in production-grade Bayesian Optimization pipelines. Specifically:
- **Warm-start priors:** encoding existing ablation knowledge (G-series results) as priors for BO
- **Multi-objective:** simultaneously optimizing nDCG@10 + MRR + latency (not just nDCG)
- **Adaptive sampling:** stopping early when convergence is detected

If you work on HPO and want to apply it to a real IR system, open a GitHub issue tagged `[lab-collab]`.

### Multi-lingual Dataset Curation

Native speakers are needed to:
- Review machine-translated golden queries for naturalness
- Identify evaluation blind spots specific to each language (PT-BR idioms, German compound nouns, etc.)
- Provide 10–20 culturally-specific test cases that machine translation would miss

Languages needed: **PT-BR** (highest priority), **ES**, **DE**, **FR**. Open a GitHub issue tagged `[lab-multilingual]`.

### EverMemBench Evaluation

Ideally, this comparison would be conducted collaboratively with the EverMind team — sharing evaluation infrastructure, ensuring identical preprocessing, and co-publishing results. A gracious comparison (where both systems acknowledge each other's strengths) is scientifically stronger than a competitive one.

If you're affiliated with EverMind-AI or the EverMemBench project, reach out via GitHub issues or email (see `CONTRIBUTING.md`).

### Scale Stress Testing

If you have a production corpus of 150k+ chunks and are willing to share anonymized data for Lab research, we want to hear from you. Corpus requirements:
- Chunks in nox-mem schema format OR convertible from Markdown/JSON
- Anonymization acceptable (strip PII, keep structure)
- Willing to be credited as "contributed corpus" in the audit doc

Open a GitHub issue tagged `[lab-corpus]`.
