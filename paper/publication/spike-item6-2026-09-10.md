> **Por que este documento existe.** A voz kimi, ao revisar o plano de conserto do Paper 1
> (2026-09-09), colocou a **decisão** sobre o item 6 antes do item 5: rodar mais

## ⚠️ Errata do próprio spike, 2026-09-10 — eu citei o README como se fosse medição

A tabela acima dizia, para o EverOS, *"importa sem key; README: **No API key or server
setup required**"*. A primeira metade é medida. **A segunda é uma frase do README que eu
copiei sem a confrontar com o código** — e o código diz outra coisa.

Medido no pacote v1.3.1:

| fato | evidência |
|---|---|
| instala e **importa** sem credencial | venv descartável; `import everos` → `1.3.1` |
| o **CLI não tem `add`/`search`** | `everos --help` → `init · demo · server · cascade · config`. O *"one command"* do README é o **`demo`** (TUI), não a superfície de benchmark |
| as superfícies programáticas são **async** | `everos.service.memorize.memorize(payload, *, is_final, defer_extraction)` e `everos.service.search.search(req: SearchRequest)` — as duas `async def` |
| **a busca instancia clientes de LLM** | `service/search.py` define `_get_llm_client()` e `_get_decider_client()`; `search()` despacha para `_get_manager().search(req)`, construído de forma preguiçosa |
| credencial é **nula por default, não dispensável** | `config/settings.py`: cada slot tem `api_key: SecretStr \| None = None` e `base_url: str \| None = None` |
| e é **agnóstica de provedor** | um dos slots de LLM já tem default `"google/gemini-3-flash-preview"`; embedding é `Literal["deepinfra","vllm","dashscope"]` sobre protocolo OpenAI, com `base_url` sobreponível |
| armazenamento | markdown + LanceDB (`everos cascade` = *"md → LanceDB sync queue"*) |

**Conclusão corrigida, e ela é melhor que as duas anteriores:**

- a razão impressa no paper (*"requires OpenRouter + DeepInfra, not available to this
  study"*) **expirou** — não são obrigatórios, e o `base_url` é sobreponível;
- a minha (*"não precisa de key"*) **estava errada** — uma corrida real de retrieval
  precisa de provedor de LLM **e** de embedding;
- o que é verdade: **os provedores são configuráveis e nós temos chave Gemini**, que é
  inclusive o default de um dos slots. O gap fecha com credencial que já temos, sem
  contratar terceiro.

🔑 **A lição é a que este projeto já registrou e eu repeti hoje:** *promessa no cabeçalho
não é implementação.* Um README que diz "no API key required" está a descrever o caminho do
`demo`; o caminho do benchmark é outro, e só o código responde qual. Eu escrevi o artefato
com a frase do README dentro de uma tabela cujo cabeçalho dizia **"medido"**.

## Adenda 2026-09-10 — o adapter existe; faltam DUAS decisões suas

`eval/q4-comparison/adapters/evermind.py` foi reescrito contra a API medida da v1.3.1
(a versão anterior falava com um CLI `evermind retrieve` que não existe em EverOS
nenhum). Suíte: `test/test_evermind_ingest.py`, 16 casos, **7 mutações mordem**.
`validate()` devolve `ok: true` sem tocar a rede.

### (1) Qual superfície — e é uma escolha de justiça, não um default

O EverOS tem duas, e **não são intercambiáveis** para nDCG por chunk-id:

| superfície | ingestão | o que volta | serve para nDCG@10? |
|---|---|---|---|
| `service.memorize` + `service.search` | conversa (`session_id` + `messages`) | **episódios derivados** | **não** — não há volta do hit para o chunk que o produziu |
| `service.knowledge` | `create_document(doc_id=…)` | `SearchHit.document.doc_id` | **sim** — o id do chunk faz round-trip |

O adapter usa a segunda. Consequência a declarar no §6: mede-se a **retrieval de
conhecimento** do EverOS, não a memória episódica. Mesma classe de divulgação que o
corpus-cap do mem0 já documentado.

⚠️ E há uma assimetria de granularidade real: o `search_knowledge` ordena **tópicos**,
não documentos, e um documento vira N tópicos. `top_k=k` tópicos pode colapsar em
**menos de k** doc_ids distintos — o que penalizaria o EverOS por granularidade, não por
qualidade. O adapter pede `k × 5` tópicos, deduplica por `doc_id` guardando o melhor
posto, e reporta `topics_seen` por chamada, para o write-up dizer o fator realizado em
vez de o supor. É o mesmo movimento do `threshold=0.0` do mem0: retirar um corte
específico do sistema que descartaria itens gold **antes** da pontuação.

### (2) A ingestão é PAGA — e está barrada por gate

`create_document()` roda uma extração de LLM **por documento**. Corpus medido hoje:

| arquivo | documentos | chars | ~tokens |
|---|---:|---:|---:|
| `cache/locomo.jsonl` | 5.882 | 767.654 | ~191,9 k |
| `cache/longmemeval.jsonl` | 948 | 13.372.109 | ~3.343 k |
| **total** | **6.830** | **14.139.763** | **~3.535 k** |

⚠️ **Não é "~2.482 chunks"** — 2.482 é a contagem de **queries** (`queries-rc4-all.jsonl`),
e eu citei esse número como se fosse o corpus. Mesma classe do `au[0]`: número certo,
população errada. E o custo está concentrado onde não parece: o LongMemEval é **14% dos
documentos e ~95% dos caracteres**.

`ingest_corpus()` **recusa** sem `EVEROS_ALLOW_PAID_INGEST=1` e devolve a estimativa em
vez de gastar. Nenhuma chamada paga acontece por acidente; o teste prova que o gate é o
que segura (mutá-lo põe a suíte vermelha).

O provedor é configurável por env OpenAI-compatível (`EVEROS_LLM__*`,
`EVEROS_EMBEDDING__*`), logo dá para correr **tudo em Gemini** — o que mantém a
comparação alinhada com a variante rc4 all-Gemini em vez de introduzir um segundo
provedor. Falta só a sua ordem para gastar.

## Adenda 2 — PREFLIGHT PAGO CORRIDO (10-09, ~13h50 BRT). O encanamento fecha.

Toto autorizou o gasto. Antes da corrida de 6.830, preflight de **5 documentos** —
e ele apanhou **duas** coisas que a assinatura não podia mostrar.

### O pipeline tem TRÊS passos, não um

```
create_document()   →  escreve APENAS markdown          (LLM: 1 extração/documento)
cascade sync_once() →  deriva o índice do markdown      (EMBEDDING: 1/tópico)
search_knowledge()  →  consulta o índice                (RERANK: 1/consulta)
```

🔴 **Medido: 5 documentos "created" com sucesso deixaram `knowledge_documents` em 0
linhas, `knowledge_topic` (LanceDB) em 0, e a busca devolveu 0 hits.** Não é defeito do
adapter — é a arquitetura *local-first* do EverOS: **o markdown é a fonte de verdade e o
índice é derivado**. Em produção um watcher alimenta a fila; num processo só, o passo é
`cascade sync`. Sem ele, a corrida completa teria produzido markdown e **zero** busca.

E antes disso, um segundo buraco: criar os diretórios **não cria o schema** — o primeiro
`create_document()` morria em `no such table: knowledge_documents`, enquanto o log dizia
`sqlite_engine_built` (o engine existe, as tabelas não).

### O que o preflight PROVOU

| pergunta | resposta medida |
|---|---|
| chave `AQ.` do Gemini serve os endpoints OpenAI-compat? | **sim** — chat 200, embeddings 200 |
| dimensão do embedding | **3072** — igual à produção do nox-mem e à variante rc4 |
| `create_document(doc_id=X)` preserva X? | **sim** — `doc_id=conv-26::D1:2` no log e no nome do diretório |
| `SearchHit.document.doc_id` volta igual? | **sim, 5/5** — nDCG@10 sobre `gold_chunk_ids` é definível |
| tópicos por documento (LoCoMo curto) | **1,0** — 2 linhas de índice por documento |
| ritmo | **1,93 s/documento** ⇒ 6.830 ≈ **220 min (3,7 h)** de ingestão |

O documento cujo texto virou a consulta saiu em **#1**.

### 🔴 O que o preflight DESCOBRIU e é decisão sua: o TERCEIRO provedor

`search_knowledge()` chama `_require_search_providers()`, que **aborta** sem reranker. E:

- a lista é fechada — `deepinfra | vllm | dashscope`. **Gemini não entra**, e os schemas
  diferem entre si, logo não há atalho OpenAI-compat;
- existe um caminho **sem** reranker no código (`_enrich_with_content`, *"acts as a
  no-reranker path"*), mas o `_require_search_providers()` aborta **antes** dele, em
  **todos** os `method` (`keyword`, `vector`, `hybrid`);
- o default de fábrica é **`Qwen/Qwen3-Reranker-4B`** na DeepInfra.

Para provar o encanamento sem pagar um quarto provedor, subi um reranker **local de
identidade** (`scripts/rerank-identidade-local.py`, contrato vLLM, devolve a ordem de
chegada). ⚠️ **Não é configuração de medição**: com ele mede-se o *recall* do EverOS
(RRF de sparse+dense) **sem** o cross-encoder que ele exige de fábrica.

**E o confound que atravessa as três opções:** o EverOS **exige** rerank; o cross-encoder
do nox-mem é **opt-in** e os números canônicos do paper são **sem** ele. Comparar
EverOS-com-rerank contra nox-mem-sem-rerank é confound de pipeline — a mesma classe que
a variante rc4 foi construída para controlar no embedding.

| opção | mede | custo | honestidade |
|---|---|---|---|
| **A** DeepInfra com `Qwen3-Reranker-4B` | o EverOS **como ele é entregue** | 4º provedor, conta nova, dinheiro | mais fiel ao sistema; **precisa** do nox-mem com cross-encoder ligado para ser justo |
| **B** cross-encoder local pelo contrato vLLM | EverOS com **o nosso** reranker | zero | reranker vira variável **controlada** nos dois lados — mais justo, menos "EverOS de fábrica" |
| **C** reranker de identidade | **recall** do EverOS, sem rerank | zero | só publicável rotulado como recall, ao lado do nox-mem sem cross-encoder |
